## 项目经验

**[起止时间]**　　**基于 QCS8550 和 GenieX 的 Qwen3.5-4B-VL 端侧多模态推理部署**　　**[项目角色：端侧推理部署 / 工程实现]**

**项目介绍：** 在 Qualcomm QCS8550 ARM64 开发板上，基于 GenieX llama_cpp 插件部署 Qwen3.5-4B-VL 多模态模型，完成 Q4_0 语言模型与匹配 F16 mmproj 视觉组件加载，实现真实图片 + 文本输入的端侧推理和 OpenAI 兼容 HTTP 调用，并整理可复现交付材料。

**技术栈：** Python / GenieX / llama.cpp / GGUF / QCS8550 / HTP NPU / FastAPI / Streamlit / Docker / RAG / Linux

1. 基于 QCS8550 QTI Linux/aarch64 环境完成 GenieX 运行时、llama_cpp 插件、Qwen3.5-4B Q4_0 主模型及 F16 mmproj 视觉组件的适配和加载，打通端侧多模态推理链路。

2. 使用真实图片通过 GenieX POST /v1/chat/completions 完成图片识别，返回 finish_reason=stop，记录 prompt_tokens=34、completion_tokens=27，验证模型、视觉组件、图片字段和 HTTP 接口协同工作。

3. 完成 QCS8550 板端 30 分钟串行稳定性测试：连续图片请求 38 次，成功 38 次，成功率 100%，平均响应时间 17.78 秒，P95 18.10 秒；同步记录可用内存、温度传感器和错误日志，未观察到明显内存持续下降。

4. 针对 HTP 缓冲区分配失败、mmproj 不匹配、模型加载失败、ABI/动态库冲突和图片输入异常等问题建立排查流程；结合 n_seq_max=1 的运行约束，形成单请求串行策略和故障边界。

5. 在 PC 主机侧实现 FastAPI 业务层和 Streamlit 交互页面，提供 /ready、图片问答、OCR、RAG 查询接口；补充输入校验、上游错误映射、超时处理和本地单元测试，8 项测试全部通过。

6. 编写模型制品清单、SHA-256 校验、启动/停止、性能测试、并发阶梯和恢复演练脚本，整理 README、板端编译说明、GenieX 使用注意事项和常见错误文档，形成可发布的 GitHub 复现仓库。

## 面试口述版

这个项目是在 QCS8550 开发板上使用 GenieX 的 llama_cpp 插件部署 Qwen3.5-4B-VL。我使用 Q4_0 的语言模型和匹配的 F16 mmproj 视觉组件，通过 OpenAI 兼容的 HTTP 接口发送真实图片和文本，验证了端侧多模态推理链路。之后做了 30 分钟串行稳定性测试，共 38 次请求全部成功，平均响应 17.78 秒，P95 是 18.10 秒。工程上我还实现了 FastAPI 和 Streamlit 业务层，加入健康检查、图片校验、OCR、RAG、错误处理、制品哈希和复现文档。当前并发上限和更长时间 soak 属于后续工程化验证项，所以我会把项目定位为已经完成核心部署和验证的工程项目，而不是声称已经达到生产 SLA。
